# Verify scenario pack: real-UI flows in the harness

The required verify checks drive chrome.* directly (by design) and the
smoke scripts cover one happy path each. Add a UI-driven scenario pack —
the flows a human would regression-test by hand — following the smoke
scripts' established structure (best-effort tier unless a scenario proves
rock-solid):

- Approval flow: a page tool without auto-run → approval card renders →
  approve runs it, deny records the denial in the call log; skip-for-
  session honoured on the second call.
- Stop mid-turn: send, stop while streaming, transcript left consistent,
  composer re-enabled.
- Tab switch mid-turn: the turn keeps writing to its chat (card 77's
  guarantee) — switch demo tabs, assert no bleed.
- History via UI: open a previous chat, delete another, empty state.
- Inspector: server tools listed with origin badges after MCP discovery
  (fixture MCP server or skip-with-reason if none reachable).
- Wire the tiers: npm run verify (required), verify:smoke (options +
  live + scenarios), documented in docs/07 if card 110 landed it.

- **claude** (2026-08-24T23:25:00.000Z): **Sharing-gate + selection scenario (verify/checks/sharingGateScenario.mjs), no model.** Drives the real gate end to end: a genuine `window.getSelection()` Range on the demo page (same technique as verify/checks/pageContext.mjs) -> SelectionChip appears -> "Stop sharing this page" hides BOTH the chip and the page's tools everywhere (Inspector's per-origin badges, the "Tools (N)" tab count drops the number entirely, not just to a lower one) -> "Share this page" brings both back, including the selection (never cleared, only un-pulled — src/sidepanel/stores/pageSharing.svelte.ts's own contract). State asserted directly: `ContextChip`'s own `data-sharing` DOM attribute, not just visible text.
  **A genuine bug found while wiring the selection-chip step: never use `panel.bringToFront()` on the panel tab.** The harness's panel is opened as an ordinary browser TAB (MV3 side panel UI cannot be opened programmatically). `initPageSharingSync`'s pull is wired to the panel's own `window` "focus" DOM event — the real product's docked side panel can receive that without changing which tab is active, but in the harness, activating the panel's OWN tab via `bringToFront()` deactivates the demo tab and breaks tab-sync outright (measured: the whole page section drops to "0 tools", tracking a `chrome-extension://` tab instead). Fixed by dispatching the same event directly — `panel.evaluate(() => window.dispatchEvent(new Event("focus")))` — which exercises the exact listener without needing a real (and here, harmful) tab switch. Worth remembering for any future scenario that needs a panel-focus gesture.

- **claude** (2026-08-24T23:40:00.000Z): **History scenario (verify/checks/historyScenario.mjs), no model.** Seeds the shared six-chat fixture (src/infra/chrome-storage/testing/storage-fixtures.mjs, same one `npm run dev:seed` and screenshots.mjs use), opens History via the real overflow menu, opens a non-active previous chat (asserts the transcript AND the `tabchat:` storage pointer moved), deletes a different chat from History (row disappears, `chat:index` shrinks), then deletes every remaining chat — including the one left open — to reach the genuine empty state. That last step leans on a real product guarantee, not a harness trick: `ChatService.startNewChat`'s own comment says the fresh chat minted when the current one is deleted is carried IN MEMORY ONLY until it gets a first message (persisting an empty placeholder immediately would put a "(no messages yet)" row at the top of History) — so never sending a message after the last delete genuinely empties the list rather than leaving a stray. Asserted `chat:index` itself reads back `[]`, not just the DOM.
  **One real discrepancy found, not a bug:** `HistoryListItem` renders titles through `titleFromSummary` (src/domain/chat/title.ts), which truncates to 48 chars + "…" IN THE DOM, not just visually — a `getByText`/`hasText` match against the full ~57-char seeded prompt finds nothing. Every locator here matches a 30-char prefix instead (`titleNeedle()`), safely inside the truncation boundary for all six seeded prompts.

- **claude** (2026-08-25T00:00:00.000Z): **THE BIG FINDING — a real, reproducible tab-tracking race, not specific to this card.** Building the two Ollama-gated scenarios, `verify/checks/liveSmoke.mjs`'s own pre-existing "panel picks up the active demo tab" assertion started failing too, unmodified. Isolated it with a throwaway repro (no seeding, no storage write, no LLM — just `panel.goto()` TWICE then `context.newPage()` for a second tab): reloading the panel's own tab and only THEN opening a second tab reproducibly races `src/infra/chrome-runtime/tab-sync.ts` into mis-tracking the newly active tab as `restricted`, and it does not self-heal (reloading OR closing/reopening the SECOND tab as a brand-new one didn't recover it in repeated trials — the panel side stays stuck). Reversing the order — open every other tab FIRST, reload the panel LAST — reproduced clean 12/12 in the same isolated repro, and has now been clean in every scenario run since. Fixed at the root: `verify/lib/liveOllama.mjs`'s `seedLiveProvider` is now split into `writeLiveProviderStorage` (nav + write) and `reloadIntoSeededWorld` (the reload, called only after every other tab this run needs already exists) — `reloadIntoSeededWorld`'s own doc comment has the full writeup. Applied to `liveSmoke.mjs` (now fixed as a side effect — was failing on every run before this), `approvalScenario.mjs`, `turnControlScenario.mjs`, and `inspectorScenario.mjs`'s own (smaller, MCP-only) seed helper. **This is a product-adjacent bug** (src/infra/chrome-runtime/tab-sync.ts or src/background/sw.ts's tab-activation handling), not a verify/ quirk, and card 112 does not fix it there (out of territory) — worth its own follow-up card; a human reloading the extension's panel tab right after switching tabs could plausibly hit the same "stuck restricted" state for real.
  **Second, smaller finding, same investigation:** `ApprovalCard`'s `aria-label` runs the tool name through `isolateLtr` (src/ui/bidi.ts), wrapping it in U+2066/U+2069 (invisible LRI/PDI marks) — a literal `"Approval needed: add-note"` regex never matches the real accessible name even though the card is genuinely on screen. Matching on `/add-note/` alone (no prefix) sidesteps it; approvalScenario.mjs's own comment has the detail for the next script that locates a card this way.
