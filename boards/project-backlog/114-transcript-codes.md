# Persisted transcripts store codes, not prose

Implement decisions/38-transcript-stores-codes-not-prose.md: the turn
engine (src/domain/chat/turn.ts, sign-in adjacent notes, tool-call status
texts) stops composing English prose into persisted TranscriptEntry
values. Notes carry a kind + params (error code, tool name, affordances);
the transcript renderer maps them through messages at display time via a
shared UI module (the established *Message.ts pattern). Pre-release: no
migration — the write path changes; stored prose notes render via a legacy
passthrough branch or are left to eviction. Update the typed fixtures and
any screenshot seeds; the chaos/turn suites assert kinds instead of
sentences.

- **claude** (2026-08-25T09:40:00.000Z): **What is NOT a note, and why — the two judgment calls.**
  **1. `fenceUntrustedContent` stays exactly where it is, untouched (src/domain/chat/message.ts).** Checked the actual write path rather than the card's description: the wrapper is applied ONLY inside `toModelMessage`, on the way out to the provider. `TranscriptEntry.content` holds the raw, unfenced tool result, and ToolCallRow renders that. So the fencing text is PROMPT-SIDE ONLY and is never persisted — it is model-facing framing, not user copy, and decision 38 has no claim on it. Same verdict for `buildSystemPrompt` (turn.ts:215-256).
  **2. But that precedent cuts the other way too, and it is what unblocked the tool kinds.** A `role:"tool"` entry's content is dual-audience: the user reads it in the row AND the model reads it back on the next round. Storing `content: ""` plus a kind would have handed the model an empty tool result — and the system prompt explicitly tells it to acknowledge a denial plainly. So `noteForModel` (message.ts, next to `fenceUntrustedContent`) expands a kind into English at prompt-assembly time, at exactly the seam the fence already occupies: transient, one-way, invisible to the transcript. Pinned by a test that a note's `content` is still `""` after `toModelMessage` reads it, and by one that a note on an untrusted-content tool entry is NOT fenced — the fence claims a web page wrote the text, and this text is ours.
  **3. The clip marker is deliberately left.** `truncate`'s `"\n… (truncated)"` (turn.ts) still lands inside stored tool-result content. Its own doc comment names the model as the reader ("a bare '…' would read as the tool's own output"), it sits inside a payload that is already arbitrary page-authored text which the row shows verbatim on purpose, and it is neither a note nor a status text. Left, journalled, not smuggled in.
  **4. Sign-in notes: there are none.** src/domain/tools/sign-in.ts returns `{status:"error", message}` results rendered by the OPTIONS page; nothing in that flow writes a `TranscriptEntry`. The card's "sign-in adjacent notes" line has no target.
  **5. The infra-authored English residue, named so it is not mistaken for an oversight.** A `provider-error` note's params still carry an infra client's own wire text (`unreachable-or-cors`/`not-supported` messages, `fix.label`/`fix.command` — e.g. Ollama's "connection closed before a completion signal" stream-truncation message, src/infra/ollama/client.ts:759-768). That is pre-existing, already-documented debt (src/ui/providerMessage.ts's header states the same boundary) and localizing it means giving `ProviderError` codes for infra failures — a change to the providers vocabulary, not this card's. Everything the DOMAIN itself would have said is now a kind.
