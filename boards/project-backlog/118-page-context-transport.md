# Page context: relay extraction and transport

First card of decisions/40-page-context-access.md: the relay learns to
answer two pull requests — current selection (document.getSelection,
trimmed, with a has-more flag if collapsed/empty distinctions matter) and
a page-text extract (dependency-free DOM walk: visible text with heading
structure and link text, scripts/styles/nav noise skipped, hard
size-capped with a truncated flag; measure a few real pages to pick the
cap and journal it). Two new protocol messages via the single-sourced
message list (infra/chrome-runtime/protocol.ts) routed like get-tools
(panel → worker → relay, timeouts on the existing ladder). Domain:
PageContext model in the chat context (selection/extract + url/title +
truncation), a driven port for pulling it, the worker/relay plumbing as
the adapter. No UI in this card — prove it end to end with unit tests
(extraction against jsdom fixtures incl. a noisy page) and a verify-level
probe (control-page message round-trip against the demo page, following
the existing runtime.mjs pattern).

- **claude-opus** (2026-08-24T13:35:00.000Z): **The cap: 16,000 UTF-8 BYTES** (`PAGE_EXTRACT_CAP_BYTES`, src/infra/dom/page-extraction.ts:38-80). Measured against three jsdom fixtures, pinned as assertions in src/infra/dom/page-extraction.test.ts:360-390 so the justification cannot drift from the code:
  - article-like page (~2,400-word post inside `<main>`, wrapped in header/primary nav/related-`<aside>`/footer): **13,430 bytes, truncated:false**. A LONG article fits whole; a typical 800-1,500-word post lands at 5-9 KB, about half the budget.
  - nav-heavy app shell (60-item sidebar menu, `role="navigation"` breadcrumbs, 90-link footer farm, hidden toast, thin content pane): **62 bytes** — `"# Dashboard\n\nYou have three open items and one overdue review."`. The `<main>` preference plus the noise heuristics do the work here; the cap never comes into it.
  - synthetic huge page (600 paragraphs, ~317,000 chars): **capped at exactly 16,000, walk takes ~40ms under jsdom** (Chrome's DOM is faster per node).
  BYTES not characters, deliberately: the budget being protected is the model's context window, and the same character count in CJK costs ~3x — a character cap would let one page through at 3x another's budget (pinned at src/infra/dom/page-extraction.test.ts:237). 16 KB ≈ 4k tokens, which leaves room for the conversation on the 8k-context local models this extension targets (decisions/04). decisions/40 requires the cap to be user-visible in the truncation note, so this number is a stated contract, not a tuning knob.

- **claude-opus** (2026-08-24T13:40:00.000Z): **How the walk works** (src/infra/dom/page-extraction.ts:406-500). Iterative with an explicit stack, not recursive — a nested-`<div>` comment thread reaches thousands of levels and would blow the JS stack (pinned with a 5,000-deep fixture). Root selection prefers `main, [role=main]`, then `article`, then `body`, re-walking the body if the preferred root came back empty. Skips `SCRIPT/STYLE/NOSCRIPT/TEMPLATE/IFRAME/SVG/CANVAS/VIDEO/SELECT/OPTION/…`, the three noise landmarks decisions/40 names (`NAV`, `FOOTER`, `ASIDE`) plus their ARIA equivalents (`role=navigation|banner|contentinfo|complementary|search`), and hidden subtrees. `HEADER` is deliberately NOT noise — an article's own `<header>` is usually where its `<h1>` is. Visibility is three cheap attribute checks (`hidden`, `aria-hidden="true"`, inline `display:none`/`visibility:hidden`) plus `Element.checkVisibility()` where the engine has it; `getComputedStyle` was rejected as the same information at many times the cost on every element of every page. Headings emit a Markdown `#`-run, list items a `-`; link TEXT is kept and the `href` never is (bytes nobody asked for, and a target the model must not be handed). Breaks are DEFERRED and coalesced, so `</div></div></p><p><div>` collapses to one paragraph break with no post-processing pass. Two safety valves: the byte cap, and `MAX_NODES_VISITED = 200_000` for the other pathological shape (a huge, mostly-hidden DOM that yields almost no text) — hitting either reports `truncated: true`, which is honest.

- **claude-opus** (2026-08-24T13:50:00.000Z): **Message shape: ONE request/response pair with a `mode` field**, not two message types — `runtime:get-page-context` / `runtime:get-page-context-response` (src/infra/chrome-runtime/protocol.ts:150-200, registered in `RUNTIME_MESSAGE_TYPES` at :251). The card left the judgement open; the two modes differ ONLY in which DOM read the relay performs, and the routing, the timeout rung, the restricted/unreachable handling and the response shape are identical down to the field — two message types would be two identical routes through sw.ts and two identical branches in the relay's `onMessage`, kept in step by hand, which is the drift `RUNTIME_MESSAGE_TYPES` exists to prevent. If a third mode ever needs a genuinely different response (structured DOM), that earns its own message. `isRuntimeMessage` stays single-sourced: the two literals were added to the `Record<RuntimeMessage["type"], true>` and the compiler required exactly that. Note there is deliberately NO `runtime:page-context-updated` push — the ABSENCE of a notification message is what makes decisions/40's "no background reads" a property of the protocol rather than a promise about panel behaviour. Response payload is the domain type, carried the way `SerializedTool` already is (re-exported from the protocol module at :44-54).

- **claude-opus** (2026-08-24T13:55:00.000Z): **Timeout rung: `SW_PAGE_CONTEXT_TIMEOUT_MS = 3_000`** (src/infra/webmcp/timeouts.mjs:54-79), the PULL tier alongside `SW_PULL_TIMEOUT_MS`, explicitly NOT part of the call-timeout ordering invariant. Justified in the file: a tool call is arbitrary page-authored code (hence 20s), while a page-context pull is `getSelection()` or one bounded synchronous walk that stops at the cap — measured at ~40ms on a 317k-char page. The only thing that can make it slow is a page whose main thread is already wedged, which is exactly what the pull tier was sized for; a 20s budget would make a user pressing Send on a hung page wait 20 seconds to be told the page could not be read. It is its own constant rather than a reuse so a later cap change can move one without silently moving the other. The relay side is NOT wrapped in `callWithTimeout` (src/content/relay.ts:455-500 explains why): both reads are bounded by construction and neither awaits anything page-authored, so the only failure a timer could catch is "the listener never ran at all", which is the worker's rung by definition.

- **claude-opus** (2026-08-24T14:00:00.000Z): **Domain home: `chat`, and the name is `PageContextSnapshot`.** src/domain/chat/page-context.ts:1-143, exported through the barrel. `tools` models what a page OFFERS and what the model may DO to it; a selection or an extract is text a human decided to put into a conversation on one turn, exactly like the text they typed — conversation input, so `chat`, which is also what decisions/40 says ("carried on the turn options"). The transport being the same relay channel a tool call uses is an adapter fact and never decides ownership. **NAMING COLLISION, and cards 119/120 need to know:** `PageContext` was ALREADY taken in src/domain/chat/ports.ts:57 and means something genuinely different — the page a turn is being RUN AGAINST (`{tabId, title, origin}`, i.e. whose tools this turn may call). Renaming that one was weighed and rejected: it is read by turn.ts and by the side panel, both being edited by other cards in this batch. So the new value is `PageContextSnapshot` (`mode`/`text`/`url`/`title`/`truncated`/`bytes`), the port is `PageContextSource`, the mode is `PageContextMode`, and the error vocabulary is `PageContextError` with kinds `Restricted | Unreachable | Unexpected` (shaped like `StorageError`, error CODES only — no user copy, so guard:i18n is untouched). Two invariants written into the types: EMPTY text is a successful answer (the usual result of a selection pull) and must never be reported as an error; and the port is pull-only BY CONSTRUCTION — no subscribe, no push — so the privacy posture is a property of the interface rather than of caller discipline.
