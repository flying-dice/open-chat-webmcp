# Page context: the sharing gate and chip UX

Second card of decisions/40 (as revised): the context chip's
"Sharing <page> · N tools" state becomes a real dismissible consent
control. Dismiss → the assistant is fully blind to the page: tools hidden
from the tools panel and picker counts, never attached to turns, no
content/selection pulls, and the chip shows a clear not-sharing state with
an equally visible re-enable affordance. While sharing is on: a
dismissible "Selected text" chip (excerpt preview, tooltip/expand) appears
when the active tab has a selection (pulled at panel focus and refreshed
at send), and a "Share page content" action toggles page-text inclusion.
Selection and content are subordinate to the gate — with sharing off
neither appears. Dismissal scope (origin/tab/navigation reset) is this
card's journalled decision; the transcript records context markers on the
user message (kinds per decision 38) rendered as localized annotations.
New strings in all ten locales; component tests over fake ports for gate
off/on, tool hiding, chip lifecycle; RTL/bidi for excerpts.

- **claude** (2026-08-24T17:40:00.000Z): **THE SCOPE DECISION: a dismissal is PER TAB, PER ORIGIN, IN MEMORY.** Implemented in src/sidepanel/stores/pageSharing.svelte.ts:71-116, keyed `` `${tabId} ${origin}` ``, and pinned by src/sidepanel/stores/pageSharing.svelte.test.ts:108-131. Each third of that was a real choice:
  - **PER ORIGIN** — navigating to a different site turns sharing back ON. A dismissal is a judgement about a PAGE ("not this one"), and carrying it across a navigation would silently make the panel useless on the next site with no visible cause. It also keeps the gesture from accumulating into a per-site blocklist nobody asked to create. Coming BACK to a tab+origin that was dismissed finds it still dismissed, which is what keying it (rather than clearing on every change) buys.
  - **PER TAB** — two tabs are two pages a user is thinking about separately. Dismissing on the tab with a password manager open must not blind the panel on the tab they switch to next.
  - **IN MEMORY, never `chrome.storage`** — closing the panel resets every key to the sharing-on default. Persisting would turn a one-off gesture into a setting with no UI to find it again; decisions/40's own answer is the always-visible re-enable instead. It also means there is no new stored shape for the pre-release no-migration rule to have an opinion about.
  The "Share page content" toggle is keyed identically and for the same reason (opting THIS page's text in says nothing about the next page's), and it deliberately SURVIVES a send — it is a standing, visible state about the page, so a follow-up question about the same page still has the page. The selection chip does not: it is consumed by the send it went with, the way an attachment is.
