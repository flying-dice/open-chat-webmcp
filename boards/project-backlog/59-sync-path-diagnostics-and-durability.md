# Make the next tab-sync failure self-explaining

Cards 54, 55, 57 and 58 are four rounds on the same reported symptom. Each round
cost a full diagnostic cycle because the failure leaves no trace: every branch
that can drop a session returns silently, and every write that can fail does so
into a `void`. Card 55 only cracked it because Jonathan hand-dumped
`chrome.storage.local` — and that avenue is now exhausted, because the dump for
card 57 shows storage is perfectly healthy while the screen is wrong.

The next occurrence needs to say which branch fired, not what is on disk.
See `decisions/25-tab-sync-ordering-and-turn-ownership.md`.

## Fix

1. **Trace the sync path.** Behind a dev-only flag (follow whatever the repo
   already does for `[webmcp]`-prefixed logging, e.g.
   `src/background/sw.ts:41`), log in `src/sidepanel/services/activeTab.ts`:
   every `onActivated`/`onUpdated` with its tabId and `changeInfo.url`; each
   `refreshActiveTab` entry and its exit reason (`stale-after-get`,
   `no-tab`, `stale-before-apply`, `tools-timeout`); and each
   `syncSessionToTab` outcome — `chatId`, `messages.length`, and whether the
   pointer resolved or a fresh chat was created.
2. **Flush on teardown.** `flushAllSessions` (`src/lib/session.ts:697-699`) has
   ZERO callers, despite `src/lib/session.ts:56-61` and `panel.svelte.ts`'s
   module doc both stating the panel flushes on unload. `selection.svelte.ts`'s
   `flush()` (`src/sidepanel/stores/selection.svelte.ts:496-500`) is dead the
   same way. Wire both to `pagehide` from `App.svelte`'s `onMount`
   (`src/sidepanel/App.svelte:130-143`), returning removal in its cleanup — so
   the debounced streaming tail (up to `MAX_WAIT_MS`, `src/lib/session.ts:158`)
   survives the panel closing. If you conclude one of them genuinely should not
   be wired, delete it and fix the doc comment rather than leaving it dead.
3. **Stop swallowing write errors.** The transcript mutators use
   `void saveSession(...)` at `panel.svelte.ts:525, 545, 561, 606, 626, 645`, so
   a rejected write is an unhandled rejection with no UI signal at all. Give
   them one shared helper that logs the failure with the chat id.
4. **`readChatRaw` distinguishes its two failure modes.** `src/lib/session.ts:299-304`
   returns `undefined` identically for "no such chat" and "record exists but
   failed `isChatSession`". Log a warning naming the chat id and the first
   failing field in the second case — that turns a silent, permanent loss into
   something a report can point at.
5. **Fix the dump script's false negative.** `scripts/dump-chat-storage.js:63-70`
   computes `everyMessageValid` over an ALREADY-coerced `[]`, so
   `chatsFailingValidation` reads 0 even when every record is corrupt — it read
   0 on the card 55 dump where all 63 records were unreadable. Report the raw
   `Array.isArray` results for `messages`/`toolCalls` separately, and mirror
   `isChatSession`'s actual checks (`src/lib/session.ts:226-240`) including
   `isToolCallLogEntry`'s `isRecord(arguments)` (`src/lib/session.ts:205-216`).
6. **Report the live session too.** The card 57 dump proved storage was right
   while the screen was wrong, but only by inference. Add the panel's in-memory
   `session` id + message count to the report (guarded — the script also runs
   from the options page, where there is no panel session) so the next dump
   shows the on-screen/on-disk divergence directly.
