# Chat domain and panel store split

Extract the chat model out of the UI, per
decisions/29-ddd-hexagonal-typescript-layout.md ("the god-store is split along
context lines; UI stores keep only view state") and the layering rules in
`.claude/skills/ddd-hexagonal/SKILL.md`. `src/sidepanel/stores/panel.svelte.ts`
is 1201 lines with ~13 getters, ~11 storage sites and 15 dependents, mixing the
session aggregate, streaming state, page info, tool lists, connection status and
per-tab selection persistence; `src/sidepanel/services/agentLoop.ts` (842) owns
the turn orchestration plus the approval contract that its own consumer imports
back. Two spine problems come with it: `PanelMessage` is persisted as a
`ChatMessage` by structural subtyping and a cast back
(panel.svelte.ts:21-32 and panel.svelte.ts:477-479), and one concept lives in two
stores (`selection.svelte.ts`, 498 lines, imports `getSessionSelection` /
`setSessionSelection` from the panel store).

## Checklist

- [x] `domain/chat` owns the `ChatSession` aggregate, the turn-phase state machine, transcript grouping and title derivation, with driven ports injected: `ChatStore`, `ModelGateway`, `ToolExecutor`, `ApprovalRequester` — pure decisions stay sync and port-free
- [x] the turn orchestration moves out of `agentLoop.ts` into `domain/chat` (`runLoop`, `streamOneTurn`, `executeToolCall`, `raceApproval`, `fenceUntrustedContent`, `MAX_ITERATIONS` 8, the "capture the target session once" tab-switch guarantee) with no `chrome.*` left in the loop — its single `chrome.runtime` site (agentLoop.ts:820) moves behind a port
- [x] `ApprovalRequest` / `ApprovalDecision` / `ApprovalRequester` and `denyByDefaultApprovalRequester` move from `services/agentLoop` into the domain; `src/sidepanel/stores/approvals.svelte.ts` (249) imports them from there, so the contract stops living in its consumer
- [x] `panel.svelte.ts` shrinks to view state only — streaming buffers, connection status, page info, tool/serverTool lists — keeping the getter-object-over-module-`$state` pattern; every persistence path goes through the injected chat service
- [x] the `PanelMessage`/`ChatMessage` cast is gone: the domain owns the persisted message shape and the panel maps it to a UI view type carrying the UI-only fields (`id`, `createdAt`, `toolArgs`, `toolStatus`) explicitly — see the journal for the deliberate deviation on which fields are actually UI-only
- [x] per-tab selection persistence leaves the panel store so `selection.svelte.ts` owns the selection concept end to end — one concept, one store
- [x] `src/sidepanel/lib/chatTitle.ts` (68) and `src/sidepanel/lib/transcriptGroups.ts` (128) take their message type from `domain/chat` instead of importing it from the store — both files moved into the context outright rather than being left as shims
- [x] npm run check, npm run build, npm run guard and npm run verify green, plus a hands-on pass over tab switching, transcript restore, rename and stop-mid-turn — done as a bare-Node exercise of the extracted domain (15 behaviours) plus the verify harness's real-browser transcript restore; see the journal

- **claude-opus** (2026-08-22T23:24:00.000Z): **Ports, and why two scopes.** The card names four driven ports; they are all injected, but at two different lifetimes, and that split is load-bearing rather than cosmetic. `ChatStore` and the approval-policy gate are per-SERVICE (`ChatServiceDeps`, src/domain/chat/service.ts:152-190) — one instance, no per-turn variation. `ModelGateway`, `ToolExecutor` and `ApprovalRequester` are per-TURN (`RunTurnRequest`, service.ts:64-79) because each genuinely varies with what the user just did: the model client comes from the current selection, the tool list from the tab in front of them, the requester from the surface running the turn. It is also what avoids a cycle: the tool executor is assembled from `services/activeTab.ts` + `services/mcpTools.ts`, both of which import the panel store, so a service constructed in the panel store could not hold one. `ModelGateway` (ports.ts:38-40) is deliberately NARROWER than `ChatProvider` — one method, `chat()` — so a turn structurally cannot list models or probe capabilities; `ChatProvider` satisfies it with no adapter in between.
- **claude-opus** (2026-08-22T23:28:00.000Z): **The fifth port the card did not name: `ChatPresenter` (ports.ts:139-185).** Moving the service into the domain meant something had to carry the state that is deliberately never persisted — which message is streaming, what phase the turn is in, whether the model answered — back out to a reactive UI, and had to answer "is this turn's chat the one on screen?" for the background-approval wait. It is one interface, keyed by chat id throughout (never "the current chat"), with a headless default so the domain runs without a UI at all. **Its `show(session): ChatSession` is the one concession to Svelte, and it is worth reading closely** (service.ts:28-38, panel.svelte.ts:136-141): Svelte 5's `$state` hands back a Proxy over an object, and mutating the raw target behind that Proxy updates the data without invalidating anything that read it — a silently stale transcript. So the service hands each session it adopts to `show` and keeps WHAT COMES BACK. The panel's implementation assigns to `$state` and returns the proxy; the default implementation is the identity function. The framework fact stays entirely in the adapter and `guard:boundaries`'s Svelte-rune scan still passes over `src/domain`.
- **claude-opus** (2026-08-22T23:32:00.000Z): **The message shape — a deliberate deviation from the checklist's wording, and the reasoning.** The card asks for a UI view type carrying `id`/`createdAt`/`toolArgs`/`toolStatus` as "UI-only fields".
