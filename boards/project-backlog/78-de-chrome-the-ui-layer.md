# De-chrome the UI layer

Components must talk to the domain through injected ports only, per
decisions/29-ddd-hexagonal-typescript-layout.md and the "UI importing
infrastructure directly" smell in `.claude/skills/ddd-hexagonal/SKILL.md`. Seven
of eleven options components call `chrome.*` directly: the worst is
`src/options/McpServerForm.svelte` (728 lines, 498 of them script) with 4
`chrome.identity` calls, 3 storage calls and the entire OAuth sign-in
orchestration inline; `ProvidersSection.svelte` (440) makes 5 permission calls
plus storage behind a header comment that claims it does not. On the side panel,
`App.svelte` reads storage at App.svelte:146 and builds the provider client inline
in `handleSend` (App.svelte:216-258), and two more components reach out directly
(`Header.svelte:16` for `chrome.sidePanel`, `ContextChip.svelte:66`). Two
duplicated re-export shims and a pair of colliding module exports get cleared at
the same time.

This card closes the DDD phase: see decisions/33-shared-ui-layer.md for the
`src/lib` → `src/ui` rename that let the last parked lint rule turn on.

- **claude-opus** (2026-08-23T01:39:00.000Z): **The OAuth split — what became a domain rule and what stayed in the adapter.** The component held ~110 lines of orchestration: host permission for the server, RFC 9728/8414 discovery, a host permission for each distinct authorization/token/registration origin, then either RFC 7591 registration + the PKCE flow or a hand-off to the manual client-id panel. **The ORDER is the rule**, and it is load-bearing rather than incidental (decisions/27: nothing may be deferred out of the click, because Chrome's tolerance for awaited work ahead of `launchWebAuthFlow` is undocumented), so it went to `src/domain/tools/sign-in.ts:107-215` as `McpSignIn`, composing `McpOAuthClient` with `HostPermissions`. The FLOW stayed in `src/infra/mcp/oauth.ts` where card 76 put it. Two details worth reading: (1) this could not have been an infra module — `src/infra/mcp` may not import `src/infra/chrome-runtime` for permissions (`adapters-do-not-import-adapters`), which is precisely why the orchestration belongs in the domain and the permissions arrive as a port; (2) `chrome.identity.getRedirectURL()` became `McpOAuthClient.redirectUri()` (gateway.ts:142-157, oauth.ts:295-302) rather than a prop, because it is the SAME string `runAuthorizationFlow` sends as `redirect_uri` — a form computing it independently could drift, and the only symptom would be an authorization server rejecting the callback. The component kept its form state machine, its `$state.snapshot` discipline and every rendered branch; `handleOAuthSignIn` (McpServerForm.svelte:340-386) is now 47 lines of "call, then branch on three outcomes".

- **claude-opus** (2026-08-23T01:50:00.000Z): **The judgment call: `src/lib` → `src/ui` (decisions/33).** `no-src-lib` cannot be honest while `src/lib` holds the shared UI kit, and card 76's own note in the config had already rejected the carve-out ("would encode 'src/lib is fine actually', the opposite of what decisions/29 concluded"). `no-cross-surface-imports` rules out pushing `markdown.ts`/`icons.ts`/`Markdown.svelte`/`providerIcon.ts` into one surface, and duplicating a markdown renderer into both bundles is worse than either naming problem. So I renamed the folder to the layer it holds and gave that layer a rule of its own — `shared-ui-is-ui-only`: `src/ui` may import `src/domain` and itself, nothing else. The `$lib` ALIAS keeps its spelling (three config lines repointed) because the shadcn CLI and ~100 vendored files write it; the FOLDER is what names the layer. Two costs I am recording rather than hiding: `src/ui/components/ui/` says "ui" twice, and the alias no longer matches its folder. Both are cosmetic, confined to the vendored subtree, and cheaper than rewriting the kit's imports so a future `shadcn add` would need reconfiguring. **Two smaller judgment calls in the same spirit:** `src/content/relay.ts` is now counted as a fourth composition root (.dependency-cruiser.cjs:55-68) — `only-roots-construct-infra` failed on it the moment I switched it on, and admitting the fourth entry point is more honest than granting it an exception, since it has its own bundle, lifecycle and infra wiring exactly as `sw.ts` does. And `dark-mode.ts` went to `src/infra/dom` rather than `src/ui`: its only two callers are the roots, it is boot-time DOM bootstrap, and putting it in infra means the lint enforces that.
