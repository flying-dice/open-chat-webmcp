## Comments

- **claude-opus** (2026-08-23T17:00:00.000Z): **The kernel, and the one property it exists for** — src/domain/result.ts:45-59. `Ok<T> = readonly [value: T, error: undefined]`, `Err<E> = readonly [value: undefined, error: E]`, `Result<T,E>` their union, exactly as decision 34 specifies. The load-bearing part is not the shape but the NARROWING, and it is fragile in a way worth writing down: `const [chat, err] = await store.getChat(id); if (err) return; use(chat)` gives `chat: ChatSession` — not `| undefined` — only because TypeScript 4.6's dependent-destructuring analysis treats element 1 as a DISCRIMINANT, which requires the success arm's error member to be the literal, un-widened `undefined`. Declaring it `E | undefined` would compile fine and silently take the value-side narrowing away from every call site in the repo. I probed this against the real strict flags BEFORE writing any of the migration (destructured form, indexed form, `Result<void,E>`, `Result<T|undefined,E>`, and a `@ts-expect-error` on the un-narrowed read — all as expected), and src/domain/result.test.ts:125-152 keeps it that way permanently: those four negative cases FAIL THE TYPECHECK if the error they expect ever stops happening, so the one edit that kills the discriminant cannot pass `npm run check`. **On `exactOptionalPropertyTypes` (card 91's warning):** it turns out not to apply at all here, and that is a reason to prefer the tuple rather than an accident — the flag governs optional PROPERTIES (`x?: T`), and a tuple declares none. Had the kernel been `{value?: T; error?: E}`, the flag's absent-vs-explicitly-undefined distinction would have become part of the contract and `ok(undefined)` — a successful read that found nothing, which is the ordinary shape of `getChat` — would have been unexpressible. Written up at src/domain/result.ts:1-42. `ok()` (no argument) is the void success and `ok(undefined)` is the found-nothing success; they compile to the same tuple and the compiler still refuses to swap them, which is the distinction src/domain/result.test.ts:140-145 pins. One extra export beyond decision 34's two: `allOk` (src/domain/result.ts:98), because fan-out is where the tuple is at its most verbose and the "walk them, bail on the first error, else collect" loop was needed at four sites in the keyed-record store and chat store alone. It is first-error-wins, deliberately — no caller in this repo shows more than one storage failure at a time.

- **claude-opus** (2026-08-23T17:15:00.000Z): **The stack, boundary outward.** src/infra/chrome-storage/area.ts:104-133 is the whole of the change in one file: the four `throw wrap(...)` became `return fail(wrap(...))`, and those four `catch`es are now the last place a platform exception exists anywhere in the tree — every method above them returns `Result<T, StorageError>` and no `throw` leaves the folder. Ports migrated: `ChatStore` (src/domain/chat/store.ts:59-98), `ProviderRegistry` (src/domain/providers/registry.ts:87-118), `ProviderDefaultsStore` + `ModelCapabilityCache` (src/domain/providers/config-store.ts), `SettingsStore` (src/domain/settings/approval-policy.ts:67-85), `McpServerRegistry` + `McpAuthTokenStore` (src/domain/tools/servers.ts:153-207). Two DOMAIN RULES over those ports moved with them: `resolveProvider`/`resolveSelection` (src/domain/providers/registry.ts) now return `Result<…, StorageError>`, and the distinction they preserve is the one I care most about in this card — a store that did not ANSWER is not the same fact as a provider the user DELETED, so a read failure is `fail(err)` and never `"dangling"`; every caller that treats it otherwise would tell the user their provider is gone when it is sitting right there. src/domain/providers/registry.test.ts pins that. Inside the adapters the tuple checks buy ORDERING rather than mapping: src/infra/chrome-storage/keyed-record-store.ts's add/update now stop after a failed core write instead of firing the credential-part writes into a `Promise.all` nobody awaited, and src/infra/chrome-storage/chat-store.ts:325-345's `commit` will not touch `chat:index` if `chat:<id>` did not land. The debounce and flush semantics are untouched; what changed is that a timer-driven flush no longer produces a bare unhandled rejection with no chat id in it (src/infra/chrome-storage/chat-store.ts:358-368 names the chat and says why dropping it is correct).

- **claude-opus** (2026-08-23T17:30:00.000Z): **Callers: three postures, chosen per site rather than uniformly.** (1) PROPAGATE, where the caller has a signature to put it in — the registries' internals, `resolveSelection`, `McpAuthTokenStore.saveAuth`. (2) ABSORB AND REPORT, where the signature cannot carry it yet: `ChatService` keeps its `Promise<void>`/`Promise<boolean>` driving API — card 95 owns changing that, per its own checklist — and its existing `reportWriteFailure` dep is renamed `reportStorageFailure` (src/domain/chat/service.ts:189) because it now receives failed READS too, with a `persist()` helper at src/domain/chat/service.ts:265 for the awaited lifecycle writes. Two behaviours there are deliberate, not incidental: `syncToTab` does NOT adopt a fabricated empty chat when the store read fails (src/domain/chat/service.ts:288-295) — swapping the transcript out on an unreadable store would show the user a blank conversation their history is still behind — and `openChat` returns `false` and reports rather than pretending the chat is missing. (3) IGNORE, but say so: the ollama capability cache (a failed read and a miss both mean "re-ask"), `resolveBaseUrl` (an unreadable store and an unset key both mean "use the documented default" — folding a `StorageError` in would have meant inventing a `ProviderError` for it and reporting a storage fault as a provider fault), the tracing flag, and `flushAll` on `pagehide`, where dropping the result is the whole point because the document is going away. `ApprovalPolicyGate` got the only genuinely NEW rule (src/domain/settings/approval-policy.ts:159-201): it FAILS CLOSED — `false`, ask the human — when a policy cannot be read, and returns a plain boolean rather than a `Result` precisely so no call site can decide otherwise. That is stricter than what an unreadable stored VALUE gets (the adapter decodes it back to the documented default), and the comment says why: a value that decodes to nothing is a known state of a working store; a `StorageError` means nothing about the user's intent is known at all. In the UI the rule was CONTROL FLOW PRESERVATION: a rejection used to abort everything after it, so every write handler in ProvidersSection/McpServersSection/HistorySection/HistoryPanel now bails on a returned error — a form that did not save must not close, a row that did not delete must not vanish, and `clearAllChats` must not empty the on-screen list for chats that are still in storage. Each logs where card 95 will render a notice. The two `throw err;` in SettingsSection.svelte STAY (they are card 95's allowlist entries); card 92 changed only their trigger, from a caught exception to a checked value.
