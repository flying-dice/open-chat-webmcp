# UI, services and composition roots consume results; throw audit to zero

Finish the errors-as-values migration at the driving edge per
decisions/34-errors-as-values.md: the chat domain service and turn engine's
own driving API, the sidepanel stores/services, both surfaces' components,
tab-sync and page-tool-executor adapters, and the four composition roots.
Every user-visible failure path (notices, test banners, approval timeouts,
storage-degraded warnings) is driven by a typed error value, never a caught
exception. Then run the strict throw audit: every surviving `throw` under
src/ is on the guard:throws allowlist with a named invariant, and the
allowlist contains ONLY programmer-error assertions (exhaustiveness,
impossible states). Boundary catch-alls (top-level error logging in roots,
the never-throws wrappers) are the only try/catch left.

- **claude-opus** (2026-08-23T20:10:00.000Z): **THE DRIVING-API DECISION, method by method — src/domain/chat/service.ts:99-128 states it in the interface doc, because the rule is the interesting part and it is not "everything returns a `Result`".** Card 92 left this service absorbing every storage failure through `reportStorageFailure` and named card 95 as the one that would change it. What I did NOT do is convert all eleven methods: a `Result` a caller cannot act on is ceremony, and it makes the ones that matter harder to spot. Three postures, chosen per method. **(1) RETURNED — the five a person drives.** `openChat` → `Result<boolean, StorageError>` (src/domain/chat/service.ts:410), `startNewChat` → `Result<void, …>` (:386), `discardIfDeleted` → `Result<void, …>` (:436), `renameCurrent` → `Result<void, …>` (:441), `setSelection` → `Result<boolean, …>` (:462). Each one is the direct consequence of a click, so its caller has an affordance for the failure — leave History open, keep the form up, show a notice. `openChat`'s three-way answer is the clearest gain: `ok(true)` opened, `ok(false)` that chat is gone, `fail(err)` the store did not answer. Card 92 had to collapse the last two into `false` because `Promise<boolean>` had nowhere else to put them, and those are exactly the two a History view should not say the same thing about. **(2) ABSORBED AND REPORTED — `syncToTab` (:321) and `applyNavigation` (:360) keep `Promise<void>`.** Their only driver is a `chrome.tabs` event (src/infra/chrome-runtime/tab-sync.ts:230-233): nobody asked for the swap, nothing awaits the answer, and there is no surface to tell. Their recovery lives inside them and the reason goes to `reportStorageFailure`. Handing a `Result` to an event listener would have meant inventing a caller for it. **(3) NOT ASYNC AT ALL — the transcript mutators.** They persist fire-and-forget so a token stream never waits on a write; same sink, and `save` at src/domain/chat/service.ts:284-296 says so. `runTurn` also stays `Promise<void>`: it never throws and every failure is already transcript content (a terminal `{type:"error"}` event with a typed `ProviderError`, decisions/34 + card 93). Net effect: `reportStorageFailure` still exists, but its doc (:194-214) now closes the list rather than pointing at a future card — nothing reaches it that a caller could have been told about.

- **claude-opus** (2026-08-23T20:25:00.000Z): **One behaviour change I made deliberately, and it is the reason those signatures are worth anything: POINTER FIRST, SWAP SECOND.** `startNewChat` and `openChat` both used to `adopt()` the new session and then write the tab pointer, absorbing the write failure. That ordering is harmless while the method returns `void` and fatal once it returns a `Result`: a caller told "that did not save" would already be looking at the new chat, with the old one retired off screen and nothing to do about it. Both now write `store.setCurrentChatForTab` FIRST and only adopt on success (src/domain/chat/service.ts:394-399, :425-433), so a failed write leaves the screen truthful and History can report it while staying exactly where it is.
