# Senior design review: sizing and type hierarchy

Requested by Jonathan (2026-08-23, with a Tools-panel screenshot): the UI
mixes sizes incoherently — e.g. that panel stacks an oversized empty-state
title over near-caption section labels (THIS PAGE / MCP SERVERS), large
body copy, and large monospace tool-card titles, all inside a ~400px side
panel. Icon sizes and title/text sizes need a full review across BOTH
surfaces.

Deliverable is a REVIEW + SPEC, not code: a senior-designer pass over every
screen state (chat, transcript with activity, picker sheet, tools/call-log,
history, approval card, all five options sections, empty states, light and
dark, 320px and 400px) producing:

1. An inventory of current sizes in use (text sizes, weights, icon sizes,
   badge/label treatments) with screenshots or path:line class references
   per offender.
2. A proposed compact type scale + icon-size scale appropriate to a dense
   side panel (few steps, named roles: page title, section label, card
   title, body, caption, mono/code) mapped onto Tailwind/shadcn tokens,
   with explicit rules for which role each recurring UI element gets.
3. A decision record draft (decisions/36-…) capturing the scale.
4. A fix-list ordered by impact, scoped for the implementation card (99).

Spec: decisions/36-type-and-icon-scale.md (Proposed). Implementation: card 99.

- **claude** (2026-08-23T14:20:00.000Z): **Icon inventory — and a bug.** In use: `size={16}`×5, `size={18}`×4, `size={20}`×13, Icon's own default 24 (`Icon.svelte:98`), plus `size-1.5` (6px status dot, `ContextChip.svelte:105`), `size-2` (8px call dot, `ToolCallRow.svelte:153`), `size-4`×23, `size-8`/`size-9`/`size-10` hit targets. The bug: `Icon.svelte:114-121` renders `HugeiconsIcon`, which emits width/height as **presentation attributes** (`node_modules/@hugeicons/svelte/dist/components/HugeiconsIcon.svelte:70-77`) — so any kit ancestor with `[&_svg:not([class*='size-'])]:size-N` wins on CSS-beats-attribute. Consequence: every `size={20}` inside a Button/Command.Item/DropdownMenu.Item renders at **16px** (e.g. `ProviderPicker.svelte:335`), every `size={20}` inside `Empty.Media` renders at **24px** (`ToolsPanel.svelte:59,73,89,123`), and IconButton's documented "compact 18px glyph" (`IconButton.svelte:82`) does not exist — it is also 16px. So the numeric `size` prop is a coin-flip between authoritative and dead, with no signal at the call site. Genuinely inconsistent pairs that DO render: `ContextChip.svelte:95,132` puts a 16px favicon and an 18px chevron in one row; `Transcript.svelte:216` renders a 20px model mark beside a 12px model label.
- **claude** (2026-08-23T14:20:00.000Z): **Proposed scale** written up as `decisions/36-type-and-icon-scale.md:1-140` (status: Proposed). Base stays 14px (`text-sm`) rather than dropping to the old 13px: Figtree's x-height reads about a step larger than the system face, and every vendored kit component already declares `text-sm`, so a root override would fight the kit and rescale Maia's rem-based spacing as a side effect. Seven roles — `page-title` 24/600 (options `<h1>` only), `title` 16/500, `body` 14/400, `body-strong` 14/500, `label` 12/500 caps, `caption` 12/400 muted, `code` 13 via a new `--text-code` token with a `text-sm`-matched line-height. The governing rule: **only one thing per screen may be larger than body, and only once — anything that repeats is body, and hierarchy inside a list comes from weight and colour, never size.** Two corollaries: mono runs one step below its sibling sans (13px in body, 14px only for the approval card's subject), and a title is a noun phrase — if it needs a sentence it is a description. Icons collapse to four sizes: 6px status dot, 8px state dot, 16px glyph (everything interactive or inline), 20px mark (identity glyphs and the empty-state glyph, in a 36px tile).
