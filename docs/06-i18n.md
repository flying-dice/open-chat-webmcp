# Internationalization

The extension ships in **ten languages**. Everything it *renders* goes through
[Paraglide JS 2](https://inlang.com/m/gerre34r/library-inlang-paraglideJs);
everything Chrome reads *before our code exists* goes through `chrome.i18n`.
Two mechanisms, because the second one is a browser constraint rather than a
choice ([decisions/37](../decisions/37-i18n-paraglide.md)).

| Locale | Endonym (as the picker shows it) | Chrome `_locales` dir | Plural categories |
| --- | --- | --- | --- |
| `en` (base) | English | `en` | one, other |
| `zh-CN` | 简体中文 | `zh_CN` | other |
| `ja` | 日本語 | `ja` | other |
| `de` | Deutsch | `de` | one, other |
| `fr` | Français | `fr` | one, many, other |
| `es` | Español | `es` | one, many, other |
| `pt-BR` | Português (Brasil) | `pt_BR` | one, many, other |
| `ko` | 한국어 | `ko` | other |
| `ru` | Русский | `ru` | one, few, many, other |
| `ar` | العربية | `ar` | zero, one, two, few, many, other |

> **Translation status: machine-produced, pending native review.** The English
> source is the only copy a human copywriter has passed over (card 103). The
> other nine locales were produced per-language against that source and a fixed
> glossary, and checked mechanically — key sets, placeholders, markup and
> plural categories all hold — but **no native speaker has signed any of them
> off**. Treat a wording report from a native speaker as a bug, not a request:
> the fix is a one-line edit to `messages/<locale>.json`, and `npm run
> guard:i18n` will tell you if it broke the structure.

## The two mechanisms

**Paraglide** compiles `messages/<locale>.json` into typed functions under
`src/paraglide/` (generated, gitignored; `postinstall` runs
`npm run compile:i18n` so a fresh clone type-checks). A component calls
`m.someKey()` and gets the active locale's string:

```svelte
<script lang="ts">
  import { m } from "../../paraglide/messages.js";
</script>

<h2>{m.settingsLanguageHeading()}</h2>
<p>{m.historyListItem_messageCount({ count: chat.messages.length })}</p>
```

`m.noSuchKey()` is a **compile error** — every message is a named export with
its own `.d.ts`, so a typo fails `npm run check` rather than rendering blank.
The reverse direction (a *locale* missing a key) is not the compiler's
problem; that is what `npm run guard:i18n` is for.

The active locale comes from the strategy chain in `paraglide.options.mjs`:
`localStorage` (what the picker writes, key `PARAGLIDE_LOCALE`) →
`preferredLanguage` (`navigator.languages`) → `baseLocale` (`en`). The side
panel and the options page are documents on the same `chrome-extension://`
origin, so they share one `localStorage` and therefore one locale, with no
`chrome.storage` mirror to keep in step.

**`chrome.i18n`** covers the three strings in `manifest.json` — the extension
name, its description, and the toolbar button's tooltip. Chrome reads the
manifest before any of our code runs, so the only mechanism it accepts is its
own: `public/_locales/<dir>/messages.json` plus `__MSG_key__` placeholders,
keyed off `default_locale: "en"`. There is no runtime switch and no typing
here; Chrome picks from the **browser's UI language**, which means the toolbar
tooltip can legitimately be in a different language from the side panel. Note
the directory names use an underscore (`pt_BR`, `zh_CN`) where Paraglide uses
the BCP-47 hyphen.

## Adding a string

1. Add the key to **`messages/en.json`**, in the section its surface owns.
   Names are `surface_camelCaseDescription` (`composer_sendLabel`), or bare
   camelCase for the handful shared across surfaces (`retryAction`).
2. Write it to card 103's rules: titles are noun phrases, descriptions are
   sentences, errors say *what happened* then *what to do next*, and the
   glossary has exactly one word per concept (chat, provider, model, tool,
   page tool, server tool, MCP server, tool call, call log, permission/grant,
   enable/disable, default, add, choose, side panel, options page).
3. Call it as `m.yourKey()`. Interpolate by name: `"Rename chat: {title}"` is
   `m.header_renameAriaLabel({ title })`.
4. Add the same key to **all nine other locale files**. `npm run guard:i18n`
   fails until they are all there — that is deliberate: a missing key does not
   error, it silently renders English.
5. Run `npm test` (component tests assert through the message functions, so
   they follow copy edits) and `npm run guard`.

Never hardcode a user-visible word in a component — not even a one-word
connector. The `· updated ` between a chat's counts and its timestamp survived
three extraction cards as a bare literal and was only caught when someone read
the Arabic options page and saw one English word in the middle of an Arabic
line.

Three traps, each of which has already bitten this repo once:

- **Never write a bare `{` or `}` in message text.** The format parses it as a
  placeholder named after whatever sits between the braces. Card 101 lost a
  literal `{ }` glyph to this; `[ ]` is fine, square brackets are not special.
- **Markup lives in the message, and must survive translation byte-for-byte.**
  Ten keys carry inline `<code>`/`<strong>`/`<em>`/`<a href>` and render
  through `{@html m.key()}`. That is only safe because those strings are 100%
  developer-authored with nothing interpolated. **A message that interpolates a
  page-, tool- or server-supplied value must never go through `{@html}`** —
  split it into `_prefix`/`_suffix` keys around a plain Svelte `{expression}`,
  which auto-escapes (cards 101-102).
- **Plurals are variant blocks, and the object form does not compile.** The
  `{ declarations, selectors, match }` block must be wrapped in an **array**;
  the object form fails with "Message must have at least one variant".

## Plurals

```json
"historyListItem_messageCount": [
  {
    "declarations": ["input count", "local countPlural = count: plural"],
    "selectors": ["countPlural"],
    "match": {
      "countPlural=one": "{count} message",
      "countPlural=other": "{count} messages"
    }
  }
]
```

`declarations` and `selectors` name the inputs the *call site* passes, so they
are identical in every locale. `match` is **not**: Paraglide compiles one
branch per category and selects between them with
`registry.plural(locale, …)`, i.e. the target locale's CLDR rules. A locale
that copied English's two categories would have no branch for Russian's `few`
or Arabic's `two` — and a number that selects a missing branch renders **the
key name**, visibly, in production. So each locale carries its own category
set (the table at the top of this page), and `guard:i18n` checks it against
`Intl.PluralRules(locale)`.

Two consequences worth knowing:

- In `ru` and `ar`, `one`/`few`/`two` cover many different numbers (Russian
  `one` is 1, 21, 31, 101…), so those branches must keep `{count}` rather than
  spelling a digit out. English can write "1 tool call"; Russian cannot.
- In `zh-CN`, `ja` and `ko` there is a single `other` branch, which therefore
  has to read correctly for every number.

## Adding a locale

1. Add the BCP-47 tag to `locales` in **`project.inlang/settings.json`**.
   Casing is load-bearing — `pt-BR`, not `pt-br` (Paraglide has a history of
   tag-casing bugs, [opral/paraglide-js#549](https://github.com/opral/inlang-paraglide-js/issues/549)),
   and the file name must match the tag exactly.
2. Create `messages/<tag>.json` with the base locale's full key set. Get the
   plural categories from `new Intl.PluralRules(tag).resolvedOptions()
   .pluralCategories` — do not copy English's.
3. Add its endonym to `LOCALE_ENDONYMS` in
   `src/options/components/SettingsSection.svelte`. That record is typed
   `Record<Locale, string>` against Paraglide's generated union, so **`npm run
   check` fails until you do** — the picker cannot silently list a locale with
   no name of its own.
4. Create `public/_locales/<chrome_dir>/messages.json` with `extName`,
   `extDescription` and `extActionTitle` (underscore form of the tag).
5. If the language is RTL, nothing else is needed: `applyDocumentLocale()` in
   `src/infra/dom/document-locale.ts` sets `<html lang>`/`<html dir>` from
   Paraglide's own `getTextDirection()` before mount, on both surfaces, and the
   whole UI is built on logical Tailwind utilities (card 104).
6. `npm run guard:i18n`, then `npm run build`, then look at it.

## Switching language

The picker is the first card on the options page (`SettingsSection.svelte`).
It writes through Paraglide's `setLocale()`, which does a **full document
reload** by default — this repo leans on that deliberately: with the page gone
there is no stale render to keep reactive, and `src/options/main.ts` re-runs
the `lang`/`dir` bootstrap on the way back up. The side panel picks the new
locale up the next time it renders, from the shared `localStorage` value.
Paraglide's `{ reload: false }` escape hatch would require a hand-rolled
reactivity layer around every `m.someKey()` and is not used.

## Right-to-left

`ar` is the RTL locale. The whole UI was swept onto logical utilities
(`ms-`/`me-`/`ps-`/`pe-`/`start-`/`end-`/`text-start`/`border-s`) in card 104,
so direction falls out of `<html dir="rtl">`. Two things needed hand-work and
will need it again for any new RTL locale:

- **Directional icons** carry `rtl:-scale-x-100`; symmetric ones must not.
  Disclosure triangles whose meaning comes from a `rotate-90` are left
  unmirrored on purpose.
- **Latin identifiers inside RTL prose** (tool names, model ids, origins,
  URLs) are bidi-isolated: `dir="ltr"` on the element where there is one, and
  `isolateLtr()` from `src/ui/bidi.ts` (U+2066/U+2069) where the value is
  interpolated into an already-assembled sentence.

- **Dates and times** go through `formatDateTime`/`formatTimeOfDay` in
  `src/ui/datetime.ts`, never a bare `toLocaleString()`. The bare form
  formats in the *browser's* locale, which is not the language the user
  picked for this extension.

The non-obvious trap, and the one thing to remember when adding UI:
**anything bits-ui renders in a portal defaults to `dir="ltr"`** and stamps
it as an attribute, so CSS `direction` inherits from that rather than from
`<html dir>` and the whole popover lays out left-to-right over a right-to-left
page. It applies to `ScrollArea` and to everything built on the floating
layer — `Select`, `Popover` (and the `Command` list inside it), `Tooltip`,
`DropdownMenu`. Every such call site passes `dir={uiTextDirection()}` from
`src/ui/direction.ts`; **a new one must too.** Note the family split: Select,
Popover and Tooltip take `dir` on their **Content**, while the menu family
takes it on **`DropdownMenu.Root`** — passing it to `DropdownMenu.Content`
type-checks and does nothing.

## The guard

`npm run guard:i18n` (`scripts/guard-i18n.mjs`) is the sixth gate in
`npm run guard`. It reads `project.inlang/settings.json` — so a locale that is
*declared* but has no file is a failure, not an absence — and fails on:

| | |
| --- | --- |
| missing key | the locale would silently render English |
| orphan key | dead translation, or a rename that landed in one file |
| kind mismatch | a plural downgraded to a flat string loses the plural |
| placeholder drift | `{count}` renamed or dropped: literal braces, or a lost value |
| literal brace | text the message format will read as a placeholder |
| markup drift | a dropped `<code>`/`<a>` in the ten rich-copy keys |
| plural categories | not the locale's own CLDR set — a missing branch renders the key name |

Every one of those is silent at build time, which is the only reason the guard
exists.
